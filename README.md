# GTM — поиск заказчиков для конференц-площадки

Система находит компании, у которых **скоро** будет крупное мероприятие, и готовит менеджеру
утренний список с готовыми письмами и конкретным поводом.

Ключевая идея — в [DECISIONS.md](DECISIONS.md), план работ и сигналы — в [PLAN.md](PLAN.md).
Коротко: это не мониторинг анонсов, а календарь ожиданий. Когда мероприятие анонсировано,
площадка уже забронирована — поэтому система работает на опережение, за 3–5 месяцев.

## Быстрый старт

```bash
uv venv .venv && uv pip install --python .venv/bin/python -e ".[dev]"
source .venv/bin/activate

export GTM_DATABASE_URL=sqlite:///var/gtm.db             # без Postgres, для проверки
gtm db init                                              # схема + отметка alembic
gtm collect fns_open_data                                # универсум из демо-набора
gtm import manual --file data/manual/companies.example.csv
gtm daily --today 2026-07-29                             # весь конвейер за один прогон
cat out/2026-07-29.md                                    # утренний список
```

`db init` нужен один раз, на пустой базе; дальше схема меняется через
`gtm db upgrade`. Каталоги `var/` и `out/` создаются сами.

Обход страниц площадок-конкурентов в `daily` не входит — это десятки минут
сетевого времени, а страницы обновляются раз в сезон. Запускается отдельно
и раз в квартал:

```bash
gtm collect venue_pages --check    # сверить адреса, ничего не сохраняя
gtm collect venue_pages            # собрать
```

Без ключей внешних API система работает целиком: реестр и архивы мероприятий читают фикстуры
из `data/fixtures/`, письма собирает детерминированный шаблонный генератор. Этого достаточно,
чтобы увидеть конвейер вживую и показать его клиенту.

## Как это устроено

```
источники → факты → ожидания → фильтр ICP → досье → письмо → утренний список
                        ↑                                            ↓
                        └──────────── калибровка ← исходы ───────────┘
```

Пять звеньев и обратная связь:

1. **Календарь, а не поток.** Факты из источников превращаются в записи `expectation`:
   «у компании X примерно тогда-то ожидается мероприятие, окно контакта открывается
   за N дней до». Ежедневная работа — один запрос по этой таблице.
2. **Фильтр по масштабу.** Главный критерий — сколько человек. Мероприятие на 80 человек
   не наш клиент, даже если компания крупная. Фильтр не делает ни одного внешнего запроса.
3. **Досье.** Только для прошедших фильтр и только по убыванию приоритета — обогащение
   стоит денег.
4. **Письмо.** Повод железобетонный: «в прошлом ноябре вы проводили конференцию на 600 человек
   в такой-то площадке; если в этом году планируете, сейчас как раз время смотреть залы».
5. **Список менеджеру.** 10–15 карточек в день, markdown и CSV.

## Команды

| Команда | Что делает |
|---|---|
| `gtm db init` | создать схему (для чистой базы; дальше `gtm db upgrade`) |
| `gtm db upgrade` | накатить миграции alembic |
| `gtm import manual --file F` | импорт CSV с компаниями и прошедшими мероприятиями |
| `gtm import suppression --file F` | пополнить стоп-лист |
| `gtm collect SOURCE` | собрать один источник (`manual`, `hh`, `registry`, `events_archive`, `zakupki`) |
| `gtm collect events_archive --backfill 3` | разовый тяжёлый сбор архива за 3 года |
| `gtm expectations build` | построить ожидания из накопленных фактов |
| `gtm expectations rescore` | пересчитать приоритеты (после правки весов) |
| `gtm filter run` | применить ICP к ожиданиям с открытым окном |
| `gtm enrich run --limit N` | собрать досье |
| `gtm generate --limit N` | написать письма |
| `gtm deliver today` | выгрузить утренний список в `out/` |
| `gtm daily` | всё вышеперечисленное одним прогоном — это то, что вешается в cron |
| `gtm feedback record ID OUTCOME` | зафиксировать исход касания |
| `gtm feedback funnel` | воронка: отправлено → ответы → показы → брони |
| `gtm feedback recalibrate` | предложение по весам сигналов (вставляется в конфиг руками) |
| `gtm quarantine list` / `resolve ID ИНН` | разбор записей, не сведённых к компании |
| `gtm stats` | сводка последнего прогона и трат по API |

У большинства команд есть `--today` для прогонов на заданную дату и `--dry-run`.

## Настройка

Бизнес-логика — в `config/`, и менять её нужно именно там, а не в коде:

- `icp.yaml` — кого считаем клиентом: масштаб мероприятия, регион, размер компании,
  исключённые отрасли, коды отказа;
- `signals.yaml` — типы сигналов, веса, окна контакта, сезонность, правила скоринга
  и калибровки;
- `sources.yaml` — источники: `live` / `offline` / `off`, лимиты, стоимость вызова;
- `prompts/letter.md` — каркас письма.

Техническое — через переменные окружения с префиксом `GTM_` или `.env`:

```bash
GTM_DATABASE_URL=postgresql+psycopg://gtm:gtm@localhost:5432/gtm
GTM_DADATA_TOKEN=...            # ЕГРЮЛ: дата регистрации, штат, выручка
GTM_ANTHROPIC_API_KEY=...       # без него письма собирает шаблонный генератор
GTM_DAILY_API_BUDGET_RUB=500    # жёсткий дневной лимит, при достижении стадия встаёт
GTM_DAILY_DELIVERY_LIMIT=15
```

## Ежедневный запуск

```cron
0 7 * * 1-5  cd /opt/gtm && .venv/bin/gtm daily >> var/daily.log 2>&1
```

Один прогон в сутки в будни. Очереди, воркеры и оркестраторы здесь не нужны —
см. [DECISIONS.md](DECISIONS.md), пункт 9.

## Разработка

```bash
.venv/bin/pytest              # тесты, сеть не нужна
.venv/bin/ruff check gtm/     # линтер
```

Тесты идут на SQLite, целевая база — PostgreSQL. Схема живёт в `gtm/storage/models.py`,
изменения — через `alembic revision --autogenerate`; тест `tests/test_migrations.py`
ловит расхождение моделей и миграций.

## Границы

Система **не** отправляет письма — это осознанно, см. DECISIONS.md, пункт 14.

Холодные письма для этого бизнеса не главный канал. Главный — event-агентства, второй —
договорённость с площадками-конкурентами о передаче отказных заявок. Система закрывает
прямой поиск крупных заказчиков, работу с агентствами нужно вести параллельно.
Подробнее — в PLAN.md.

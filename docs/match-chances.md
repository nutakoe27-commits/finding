# Оценка вероятностей и короткий разбор

Кнопка ИИ-разбора сначала запрашивает статистику выбранного события, затем
сохраняет фоновое задание на VPS. Формируется расчёт вероятностей.
Нейросеть сопоставляет отобранные основные рынки,
полную доступную статистику и историю. Если весь вход помещается, нейросеть сразу пишет короткие
аргументы одним вызовом. Иначе данные обрабатываются по частям с итоговым сопоставлением.
Числа вероятностей и структура отчёта формируются сервером. Произвольные
проценты из ответа нейросети не используются. Параметры расчёта не передаются
в публичный контекст.

Каждое наблюдение нейросети содержит ID и точную цитату из полученного фрагмента.
Проверяются существование источника, наличие цитаты и числовые ссылки. Итоговые
аргументы ссылаются на эти наблюдения. Это не автоматическая гарантия правильности
смыслового вывода; исходные данные и ограничения сохраняются вместе с разбором.
Поиск и непроверенные записи не превращаются в подтверждённую историю.
В новых разборах интернет-поиск отключён: Wigolo MCP не вызывается даже при
сохранённом `WIGOLO_MCP_URL`. Передаются данные Winline, архив, расчётные оценки
и помеченные как непроверенные заметки пользователя. Старые интернет-источники
в сохранённых отчётах не переписываются и не попадают в новые диагностические
запросы к модели. Для новых разборов используется другая версия ключа кэша.

Ответ содержит наиболее вероятный исход, до трёх оценённых рынков, аргументы и,
при наличии, ограничения. «Победные рынки» — название блока, а не обещание выигрыша.
Наиболее вероятный исход может иметь менее 50%, а ничья может оказаться вероятнее
победы любой команды. В интерфейсе исход и процент выделены отдельной карточкой;
оценка по котировкам имеет подпись «По линии». Рынки и аргументы показаны списками,
ограничения — раскрываемым блоком. Оформление действует и для сохранённых отчётов.

Независимая оценка в первой версии поддерживает предматчевый футбол. Требуются
достаточная история того же турнира, точная привязка участников и прошлые счета.
Оцениваются основной 1X2, двойной шанс, тоталы голов с однозначной линией,
обе забьют, точный счёт и некоторые половинные форы. Периоды, угловые,
карточки, четвертные линии и неизвестные правила не получают выдуманных оценок.
Счёт футбольного матча не используется как статистика тенниса или баскетбола.
Для live и недостаточной истории проценты по доступному однозначному рынку
помечаются «по линии»: это нормировка котировок, а не независимая оценка.

## Отбор рынков

По умолчанию нейросети передаётся не более восьми исходных рынков. Сначала
сохраняются выбор пользователя, рынок рассчитанного победителя и явно указанный
источником основной рынок. Затем выбираются разные основные семейства:
1X2 / победитель, двойной шанс, обе забьют, тотал и простая фора, победа без
ничьей, однозначные индивидуальные тоталы. При нескольких линиях одного типа
предпочтение отдаётся близким котировкам сторон, а не максимальному проценту
тривиального исхода. Это эвристика релевантности, не обещание прибыльности.

В разметке Winline строки «больше» / «меньше» и форы двух команд могут быть
разными исходными рынками. Они отбираются парой: одинаковые линии тоталов
или противоположные форы связываются по подписям; строки не обрезаются и
не смешиваются с другим периодом. Внутри отобранных рынков все исходы,
коэффициенты, параметры и состояния сохраняются. Комбинации, точный счёт,
карточки, угловые и интервалы по минутам автоматически не добавляются;
явный выбор пользователя и явно указанный основной рынок сохраняются.
Без однозначной интерпретации таблица не объявляется обычным рынком.

Сервер сначала рассчитывает оценки на полном доступном наборе. В контексте ИИ
фильтруются и рынки, и дублирующие строки `probability_assessment.markets`.
Итоговые варианты выбираются из оставшихся рынков. Показатель «получено рынков»
в диагностике ИИ относится к отбору, а `coverage.stored_markets` — к полной базе.
Интерфейс показывает «Для разбора выбрано N из M рынков».

Полный вход до отбора сохраняется в сжатом JSON в `event_analysis_inputs`,
отдельно от сокращённого отчёта. Он нужен для аудита и повторного сравнения;
второй раз нейросети не отправляется. Каталог и архив рынков не сокращаются.
`QWEN_MARKET_LIMIT=8` задаёт предел; допустимо 2–20, значение 0 оставляет все рынки.
Восемь — верхняя граница: неподходящие рынки не добавляются ради заполнения лимита.

Сравнить один и тот же сохранённый вход до и после отбора на VPS:

```bash
cd /root/matchlab
.venv/bin/python -m matchlab compare-qwen-context
.venv/bin/python -m matchlab compare-qwen-context --market-limit 5
```

Команда только читает SQLite и вызывает `/models` и `/tokenize`, без генерации
и изменения базы. `full` и `focused` содержат число рынков и исходов, размер
входа в байтах и фактические токены токенизатора; `savings` — разницу. Секции
статистики и истории остаются одинаковыми. Если токенизатор недоступен, вместо
оценочных «токенов» выводится причина ошибки. Полный снимок берётся из аудита
или старого отчёта до введения отбора; источник указан в `sample.source`.

В [примере измерения](market-context-benchmark.json) публичный сохранённый снимок
с 156 рынками / 614 исходами после отбора содержит 7 рынков / 38 исходов.
Подготовленный вход уменьшился с 212584 до 93546 байт (56,0%). Это реконструкция
для сравнения размера, без генерации и без измерения токенов модели. В ней
статистика занимает 60398 байт и не сокращается. Уменьшение числа рынков
не гарантирует, что весь контекст уложится в 32K: это проверяет токенизатор.

## Большой контекст

Прежний запрос на 139 рынков / 616 исходов занимал около 185 КБ и отклонялся ИИ.
Теперь поля отобранного входа разбиваются по JSON-путям. Длинные тексты сохраняют
смещения частей; исходы внутри отобранных рынков не обрезаются.
Окно модели читается из `/v1/models`, счётчик токенов — из vLLM `/tokenize`.
Если эти возможности недоступны, используется консервативный предел по байтам.
После `context_limit` части разделяются повторно. Промежуточные наблюдения также
объединяются по частям, чтобы итоговый запрос не переполнился.

Сначала проверяется размер полного запроса. Если он укладывается в заданный
предел входа и окно модели, выполняется один вызов с 1–2 короткими аргументами
и проверяемыми цитатами. Отдельного итогового вызова нет; резерв ответа — до
512 токенов. Число записей само по себе не создаёт дополнительные части:
прежний предел 512 записей ограничивал даже помещавшийся полный вход.
В диагностике этот режим называется `pipeline=single_pass`, обработка по
частям — `map_reduce`. Это подтверждает доставку данных и проверку цитат,
но не доказывает, что модель содержательно учла каждое поле.
Цитата копируется из `data` указанной записи, без перевода и пересказа. При
несовпадении возможна одна короткая попытка исправления на весь разбор:
модель получает только указанные ею существующие источники (не более четырёх),
до 8192 входных токенов и до 60 секунд в пределах общего бюджета. Все исходные
данные уже были переданы первым запросом; большой вход повторно не отправляется.
Исправление проходит ту же проверку цитат и чисел. Если источников нет, они
не помещаются в малый запрос или исправление не прошло проверку, возвращается
расчётный отчёт с действительной причиной. Дополнительный вызов виден в диагностике.
Для крупных запросов исходные записи объединяются в более крупные фрагменты:
повторяющихся JSON-путей и метаданных становится меньше, значения сохраняются.

По умолчанию выполняется один вызов за раз, а целевой размер входа одной части —
4096 токенов. Это отдельная настройка от полного окна модели: объявленные сервером
32K или 64K не заставляют сервис отправлять настолько большие части. Убрано
внутреннее ограничение одного вызова в 35 секунд: применяется
`QWEN_TIMEOUT_SECONDS` (по умолчанию 90) для синхронных запросов в пределах
оставшегося общего времени. Фоновые задания используют отдельный бюджет ниже.
После таймаута новые части и итоговый запрос не отправляются в занятую модель.
Разрыв клиентского соединения сам по себе не гарантирует отмену генерации на сервере.

По умолчанию синхронный этап ИИ ограничен 120 секундами и 256 попытками.
Если обработать всё не удалось, ответ
помечается частичным либо расчётным, с причиной. Неполный разбор не выдаётся
за полный и не расходует бонусный разбор. В сохранённом контексте есть число
доставленных фрагментов и полностью обработанных рынков/исходов.

Необязательные настройки в `.env` на VPS:

```dotenv
# 0: определить по /v1/models; если сервер не сообщает окно, использовать 4096.
QWEN_CONTEXT_TOKENS=0
# Целевой предел входа одной части; выход дополнительно должен помещаться в окно.
QWEN_BATCH_TOKENS=4096
# 1 для последовательной обработки; 2 только после измерения производительности.
QWEN_PARALLELISM=1
# Максимальное ожидание одного вызова, ограниченное также общим бюджетом.
QWEN_TIMEOUT_SECONDS=90
# Общее время этапа ИИ, включая разбиение и итог; допустимо 10–150 секунд.
QWEN_ANALYSIS_TIMEOUT_SECONDS=120
# Весь этап ИИ в фоновом задании; допустимо 30–1800 секунд.
QWEN_JOB_TIMEOUT_SECONDS=900
```

Не увеличивайте `QWEN_CONTEXT_TOKENS` сверх реального окна сервера модели.
Здесь не изменяются настройки vLLM и расход видеопамяти на загрузку модели.

### Долгие разборы в интерфейсе

Браузер отправляет `POST /api/{archive|bookmakers}/events/{id}/analysis-jobs`,
получает HTTP 202 и опрашивает `GET /api/analysis-jobs/{id}`. Долгий вызов модели
не удерживает соединение браузера или nginx. Итог сохраняется в личной истории.
`GET /api/analysis-jobs/current` позволяет вернуться к активному заданию после
перезагрузки страницы: повторное нажатие на том же матче продолжает ожидание.
Во время просмотра других матчей задание продолжает выполняться.

Очередь находится в SQLite, выполняется встроенным потоком приложения и не
требует новой systemd-службы. Во всей базе одновременно выполняется одно
фоновое задание; у аккаунта может быть одно активное задание, всего в очереди
не более восьми. Ожидание в очереди ограничено 30 минутами.
Обработка модели ограничена `QWEN_JOB_TIMEOUT_SECONDS`, отдельный вызов — этим
значением минус 30 секунд для подготовки и завершения. Сетевые соединения,
подготовка поиска и ожидание блокировки могут сократить фактический бюджет.

Доступ к заданиям требует действующей сессии владельца; постановка также
проверяет CSRF, текущие согласия и ограничения частоты. Лимит и бонус резервируются
один раз. Опрос и повторное получение того же задания не создают списаний.
При ошибке и расчётной сводке вместо ИИ-разбора бонус возвращается.
Задание хранит снимок матча и статистики на момент запроса: обновление линии
во время ожидания не подменяет исходные данные. Отчёт помечает устаревший снимок.

Перезапуск сайта сохраняет очередь. Прерванная работающая генерация не запускается
автоматически второй раз: её срок ожидания должен истечь, затем попытка возвращается.
Это не гарантирует отмену уже отправленного запроса на стороне vLLM.
Синхронные `/explain` сохранены для совместимости; их старые пределы остаются.

### Увеличение окна сервера

Фактически запущенный артефакт и имя API могут различаться. Например,
`--model mattbucci/Qwen3.8-27B-AWQ` с
`--served-model-name QuantTrio/Qwen3.5-35B-A3B-AWQ` обслуживает прежний API-алиас;
его не следует менять при использовании другим проектом.
В опубликованном [config.json этой модели](https://huggingface.co/mattbucci/Qwen3.8-27B-AWQ/blob/main/config.json)
указано `text_config.max_position_embeddings=262144`. Это допускает проверку
64K, но не гарантирует достаточный KV-кэш на конкретном оборудовании.
Результаты из карточки модели получены на другом оборудовании и движке.

На этом сервере одновременно работают Kokoro и Whisper, занимающие около 7 ГБ
на GPU 0. Переход на 128K с `gpu-memory-utilization=0.82` завершился OOM при
инициализации, а профиль 0.70 — OOM в Triton при первом коротком запросе.
Нельзя выбирать долю памяти только по суммарным 64 ГБ двух карт.
До перезапуска нужно знать владельца процесса и точную конфигурацию службы:
этот сервер используется другим проектом. Проверяются сообщения о размере
GPU KV-кэша, допустимой конкуренции и реальная генерация. Доступность
`/models` и `/tokenize` не доказывает исправность движка после падения.
Число `--max-num-seqs 4` влияет на планирование и для гибридной модели может
влиять на память состояний, но не означает четыре гарантированных полных окна.
Снижение этого числа также затронет другой проект и требует отдельной оценки.

Если токенизатор уже показал 100784 входных токена и 103088 с резервом,
64K недостаточно для одного полного запроса. Следующее подходящее окно — 131072.
Порядок изменения фактического запуска, проверки обоих проектов и отката описан
в [инструкции перехода на 128K](qwen-context-rollout.md).

Выбор 64K или 128K делается по токенизатору, а не по килобайтам JSON:

```bash
cd /root/matchlab
.venv/bin/python -m matchlab inspect-qwen-context
```

Команда читает последний сохранённый разбор, обращается к `/models` и `/tokenize`,
но не запускает генерацию. `raw_context` — исходный контекст;
`single_evidence_request` — все данные с теми же путями, ID источников, метаданными
и инструкциями, которые использует настоящий запрос. У второго может быть больше
токенов. `minimum_context_tokens` включает резерв ответа и 256 токенов запаса.
Тексты источников и ключи не печатаются. Если токенизатор недоступен, точное
число токенов и подходящее окно не утверждаются.
`input_sections_bytes` показывает размеры отдельных разделов без их содержимого;
это байты JSON, а не токены. По нему можно отличить объём рынков и статистики
от объёма поисковых материалов. Для нового входа поиск имеет состояние `disabled`.

После фактического запуска 64K можно проверить `QWEN_BATCH_TOKENS=60000`
на VPS, сохранив `QWEN_CONTEXT_TOKENS=0` и `QWEN_PARALLELISM=1`.
Если `single_evidence_request.input_tokens` укладывается в этот предел,
используется один полный вызов, если также хватает окна с резервом ответа.
При большем входе применяется обработка по частям. Большое окно не ускоряет обработку каждого токена;
время первого ответа и полного разбора измеряется на настоящей модели.

## Диагностика

В админке отдельно видны: «ИИ ответил», «ИИ не вызывался», «ИИ · частично»,
«Превышен контекст», «Ошибка ИИ» и «Ответ из кэша», количество вызовов и частей.
Время в таблице — выполнение фонового задания, включая поиск и подготовку,
без очереди и предварительного получения статистики; для синхронных вызовов —
время запроса к сайту. Активные задания имеют статус «В работе».
Кэш не выдаётся за новый вызов модели.
`quotation_mismatch` означает, что модель ответила, но цитата не совпала с её
источником. `unsupported_number` — число в аргументе не подтверждено цитатой.
Эти случаи не считаются переполнением окна. Ошибочная старая категория
`context_limit` в админке уточняется только если все сохранённые попытки
однозначно показывают несовпадение цитат; исходный отчёт остаётся неизменным.
Для старых записей причина восстанавливается только при однозначной связи с
сохранённым разбором; иначе остаётся «Сводка · без диагностики».

На VPS, без вывода ключей:

```bash
cd /root/matchlab
.venv/bin/python -m matchlab check-qwen
.venv/bin/python -m matchlab check-qwen-load
sudo journalctl -u matchlab.service --since '20 minutes ago' --no-pager | grep -E 'Qwen (event|part|completion)'
```

`check-qwen-load` последовательно выполняет крошечный запрос, затем один
ограниченный фрагмент сохранённого матча (до 2048 входных и 256 выходных токенов).
При ошибке первого запроса второй не отправляется. Вывод содержит длительность,
реальные счётчики токенов, причину завершения и длины ответа/рассуждения,
но не их содержание. Это измерение отклика с учётом очереди и сети, а не чистый
бенчмарк GPU. При отсутствии сохранённого разбора выполняется только первый запрос.

Журнал содержит начало и конец каждого вызова, объём входа, таймаут, время,
счётчики токенов и безопасную категорию отклонения ответа. Отдельная строка
`Qwen part accepted` подтверждает прохождение проверки цитат/структуры.
Та же диагностика попыток сохраняется в `context.ai_generation.attempts`.
При успехе видна строка `Qwen event complete: state=ready parts=N/N calls=K markets=139/139`.
Категории ошибок: `timeout`, `connection`, `proxy`, `context_limit`, `output_limit`,
`reasoning_only`, `authentication`, `model_or_endpoint`, `provider_http`, `invalid_response`.
Тексты запросов, ключи и цитаты источников в журнал не выводятся.

## Проверка качества

Проверка по действительно сохранённым до начала прогнозам, после поступления
завершённых результатов:

```bash
cd /root/matchlab
.venv/bin/python -m matchlab.chances_audit
```

Команда только читает базу, оценивает первый независимый прогноз каждого матча,
исключает повторные разборы и дубликаты пользователей. Выводит Brier score,
log loss и частоты реализации прогнозов в интервалах вероятности. При малой
выборке прямо отмечает это. Пока такой проверки на достаточном числе новых
матчей нет, оценка не называется откалиброванной; прибыльность не установлена.

## Обновление

Только на VPS сайта. Добавляется необязательное поле диагностики к существующей
таблице запросов; записи, пользователи и история сохраняются.

```bash
cd /root/matchlab
.venv/bin/python -m matchlab.manage backup &&
git pull --ff-only origin main &&
sudo systemctl restart matchlab.service
```

Сборщик на сервере нейросети использует прежний протокол одноразовых заданий.

# Переезд основной базы Matchlab на MySQL

Поддерживается MySQL 8.0.16+; проверяется на MySQL **8.0.46**, как на VPS.
MySQL самого сервера и базы других проектов не перезапускаются и не изменяются.
SQLite сборщика Winline на другом сервере остаётся на месте: переносится только
основная база сайта — аккаунты, прогнозы, архив, очереди, оплаты и доступы.

Публикация кода сама по себе базу не переключает. Пустой
`MATCHLAB_DATABASE_URL` сохраняет SQLite. Приложение отказывается запускаться
на MySQL без отметки проверенного переноса, чтобы ошибочный адрес не привёл к
показу пустого сайта вместо прежних аккаунтов.

## 1. Подготовка без остановки сайта

На VPS сайта, из `/root/matchlab`:

```bash
git pull --ff-only origin main
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/prepare_mysql.py
.venv/bin/python scripts/migrate_mysql.py
```

`prepare_mysql.py` использует локальный административный вход `mysql` через
Unix-сокет. Создаёт только новую базу `matchlab_app` и отдельную учётную запись
`matchlab_app@127.0.0.1` с правами на неё. Если база или пользователь уже существуют,
скрипт прекращает работу, не меняя их. Для другого свободного имени:

```bash
.venv/bin/python scripts/prepare_mysql.py --database matchlab_site --user matchlab_site
```

Пароль генерируется автоматически. URL хранится в закрытом файле
`MATCHLAB_DATA_DIR/mysql-target.env` с правами 0600 и не выводится. Файл не нужно
отправлять в чат или коммитить. Скрипт не меняет активное подключение.
Если вход администратора MySQL требует дополнительной настройки, остановиться
на этом шаге; рабочая SQLite остаётся активна.

Первый запуск мигратора — **репетиция**. Он создаёт согласованный снимок SQLite,
проверяет `integrity_check`, копирует все таблицы в отдельную MySQL, сверяет
количество строк и SHA-256 содержимого каждой таблицы и откатывает скопированные
строки. Таблицы новой базы остаются подготовленными, но пустыми. Исходник не
изменяется. Ожидаемый итог: `state: rehearsal_verified`, `activated: false`.

Снимки и отчёты сохраняются в `MATCHLAB_DATA_DIR/database-migrations/` с закрытыми
правами. Сверка различает NULL, целые числа, строки, вещественные числа и BLOB;
учитывает повторяющиеся строки. Кириллица, emoji, пробелы в ключах и сжатые
снимки переносятся без пересериализации. Представления и триггеры неизвестного
назначения вызывают отказ, а не молчаливое исключение.

## 2. Окончательный перенос и переключение

После успешной репетиции выбрать короткое окно обслуживания. Дождаться текущих
ИИ-разборов; не запускать другие утилиты, записывающие основную SQLite.

```bash
sudo systemctl stop matchlab.service
```

Если установлена `matchlab-push.service`, остановить и её:

```bash
sudo systemctl stop matchlab-push.service
```

Затем:

```bash
.venv/bin/python scripts/migrate_mysql.py --apply --activate
```

Создаётся **новый** снимок, чтобы включить записи после репетиции. Перед импортом
повторно проверяется пустота целевых таблиц. После копирования сверяются все
строки и контрольные суммы, а перед переключением — неизменность исходной
SQLite и остановка обеих служб. Только затем импорт фиксируется и в `.env`
атомарно записывается `MATCHLAB_DATABASE_URL`. Прежняя SQLite и копия `.env`
сохраняются. Ожидаемый итог: `state: verified`, `activated: true`.

При ошибке **не менять URL вручную, не очищать целевую базу и не удалять SQLite**.
Ошибка импорта откатывает строки целиком. Если импорт уже подтверждён, но запись
`.env` не завершилась, для завершения переключения без повторного копирования:

```bash
.venv/bin/python scripts/migrate_mysql.py --activate-verified
```

Эта команда снова сверяет обе базы и требует остановленных служб. Если после
снимка SQLite изменялась, активация запрещается: нужен новый перенос в отдельную
пустую базу. Повторный импорт поверх существующих данных всегда запрещён.

После `activated: true`:

```bash
sudo systemctl start matchlab.service
sudo systemctl status matchlab.service --no-pager
sudo journalctl -u matchlab.service -n 30 --no-pager
```

Запустить `matchlab-push.service`, если она была установлена и работала.
Проверить вход прежним аккаунтом, баланс, открытый ответ, архив и раздел оплат.
Сверить итоговый отчёт переноса: число таблиц/записей и совпадение контрольных сумм.
На время остановки сайт недоступен; отправители данных должны повторить доставку.
Мигратор сохраняет очереди и снимки, но не может перенести уже выполняющийся
процесс генерации: такая задача обрабатывается штатным механизмом восстановления.

## 3. Резервное копирование и откат

```bash
.venv/bin/python -m matchlab.manage backup
```

Для MySQL команда создаёт проверенную переносимую SQLite-копию **актуального
состояния MySQL**, в согласованном read-only снимке InnoDB. Это не копирование
старого файла до переезда. Если обнаружены неизвестные новые таблицы/поля,
копирование прекращается, чтобы не выдать неполный архив за полный. Известные
приложению добавления таблиц и полей учитываются при обновлении автоматически.
Автоматический график, внешнее хранение и регулярная проверка восстановления
должны настраиваться отдельно; копии на том же диске не защищают от потери VPS.

Нельзя просто убрать URL из `.env` после появления новых записей в MySQL: старая
SQLite их не содержит. Для отката остановить те же службы и выполнить:

```bash
.venv/bin/python scripts/migrate_mysql.py --rollback
```

Сначала выгружаются и сверяются **все актуальные** данные MySQL. Прежняя SQLite
и её служебные файлы сохраняются под другим именем. Только после проверки новая
SQLite устанавливается на её место и URL очищается. MySQL не удаляется. Затем
можно запустить службы и проверить аккаунты и балансы. При ошибке службы не
запускать до проверки; все созданные копии сохранять.

## Особенности первого этапа

- Движок InnoDB; идентификаторы и индексируемые строки — бинарные ключи для
  сохранения различий регистра и завершающих пробелов SQLite. JSON остаётся
  исходным текстом; сжатые данные — BLOB. Слишком длинный ключ вызывает отказ
  транзакции, а не усечение данных.
- Финансовые операции и захват задач пока используют общий именованный
  write-lock MySQL. Это сохраняет прежнюю последовательность проверок и
  списаний между процессами. Чтения выполняются независимо. Оптимизация на
  отдельные блокировки строк — самостоятельный последующий этап, а не часть
  рискованной смены СУБД.
- Проверки дубликатов платежей, повторных уведомлений и открытия одного ответа
  сохраняются в транзакциях и уникальных индексах. Боевые платежи не включаются.
- Некоторые сравнения названий результатов выполняются в Python, чтобы сохранить
  NFKC/casefold и правила привязки участников. Для очень большого архива это
  потребует отдельной оптимизации и измерений.
- Одноразовая SQLite-копия схемы используется только как описание таблиц.
  Данные работающего сайта после переключения читаются/пишутся в MySQL.

## Проверки разработки

`tests/run_mysql_contracts.py` запускает выбранные контракты хранения, аккаунтов,
архива, очередей и оплат на отдельном локальном MySQL. Создаёт только уникальные
тестовые схемы и удаляет их после проверки. Не запускать с реквизитами рабочей
базы. Полная проверка переноса и обратного экспорта — `test_mysql_migration`;
интерфейс оплаты — `browser_admin_billing.py`. Реальные платежи и ИИ для этих
проверок не используются.

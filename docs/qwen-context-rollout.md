# Общее окно Qwen: переход на 128K

В измеренном разборе исходные данные занимают 73799 токенов, а запрос с ID
источников и метаданными — 100784. С резервом требуется 103088. Для отправки
такого запроса целиком подходит окно 131072. Matchlab также умеет передавать
все данные частями в прежнее окно 32768.

На сервере установлен [1Cat-vLLM](https://github.com/1CatAI/1Cat-vLLM),
форк vLLM для V100/SM70. Окружение, Flash-V100 и версии пакетов сохраняются.
Увеличение окна не требует переустановки движка или замены AWQ на NVFP4.
Чужие результаты на четырёх GPU не являются замером этого экземпляра.

Фактический артефакт: `mattbucci/Qwen3.8-27B-AWQ`; API-алиас:
`QuantTrio/Qwen3.5-35B-A3B-AWQ`. В опубликованном config.json указано
262144 позиций. Доступный KV-кэш на двух V100 32 ГБ ещё не подтверждён.

## Найденный способ запуска

`/etc/systemd/system/vllm.service` напрямую выполняет
`/home/user/1Cat-vLLM/start_vllm38.sh`. В этом скрипте явно задано
`--max-model-len 32768`. Меняется только число в скрипте.
Unit, его Environment, путь запуска и остальные байты скрипта сохраняются.
Drop-in и daemon-reload для этого способа не нужны.

Скрипт содержит настройки обоих проектов: модель, API-алиас, порт, ключи,
AWQ, float16, TP=2, долю памяти 0.82, max-num-seqs и бюджет prefill.
Они не переписываются. Сохраняются владелец, группа, права и расширенные
атрибуты файла. Сам процесс модели продолжает работать с прежним окном
до явного перезапуска.

Перезапуск общей `vllm.service` прервёт текущие запросы обоих проектов
до завершения загрузки модели. Длинные запросы делят GPU и KV-кэш со вторым
проектом, поэтому прежняя задержка ответов не гарантируется.
Второй процесс модели не запускается.

## Подготовка и установка на сервере нейросети

Весь блок выполняется на сервере нейросети из checkout Matchlab:

```bash
(
  set -euo pipefail
  cd ~/matchlab-scraper-src
  git pull --ff-only origin main

  qwen_task_prepare="$(sudo python3 scripts/configure_qwen_context.py prepare \
    --unit vllm.service \
    --launch-script /home/user/1Cat-vLLM/start_vllm38.sh \
    --tokens 131072)"
  printf '%s\n' "$qwen_task_prepare"
  qwen_task_plan="$(python3 -c 'import json,sys; print(json.load(sys.stdin)["plan"])' <<< "$qwen_task_prepare")"
  sudo python3 scripts/configure_qwen_context.py apply --plan "$qwen_task_plan"
)
```

`prepare` проверяет привязку unit к указанному скрипту и один явный числовой
параметр окна. Сохраняет закрытые копии unit и скрипта, а также кандидат
в `/var/lib/matchlab-qwen-context`. Проверяет кандидат через `bash -n`
с отключёнными BASH_ENV/ENV, не выполняя команды запуска.
Ключи, Environment и содержимое исходников в stdout не печатаются.

Сохраните `rollback_command` из напечатанного JSON. Не отправляйте приватные
файлы плана в чат: они могут содержать параметры с ключами.
`kv_capacity_verified=false` означает, что bash-проверка не выделяла KV-кэш.

`apply` повторно проверяет хеши unit, скрипта и кандидата, а также владельца
и права скрипта. Заменяет скрипт атомарно. При ручном изменении файлов между
подготовкой и установкой останавливается. Ни один из двух шагов не вызывает
restart, stop или daemon-reload. Успешный результат — `script_updated`.

## Перезапуск и проверка обоих проектов

Когда текущие запросы обоих проектов можно прервать:

```bash
sudo systemctl restart vllm.service
sudo systemctl show vllm.service -p ActiveState -p SubState -p NRestarts --no-pager
```

`active` во время загрузки само по себе не означает готовый API.
На VPS после загрузки модели:

```bash
cd /root/matchlab
.venv/bin/python -m matchlab check-qwen
.venv/bin/python -m matchlab inspect-qwen-context
```

Нужно увидеть настоящий ответ Chat Completions и `context_tokens=131072`.
Также проверьте один обычный запрос второго проекта.
При повторных падениях, нехватке памяти, неработающем API или ухудшении
работы второго проекта выполните сохранённый `rollback_command`, затем:

```bash
sudo systemctl restart vllm.service
```

Откат восстанавливает исходные байты скрипта из проверенной копии, сохраняя
владельца и права. Если после установки скрипт изменён вручную, откат
останавливается и не затирает эти изменения. Он не выполняет перезапуск.
Unit и чужие настройки systemd не меняются при установке и откате.

## Настройки Matchlab после успешной проверки модели

На VPS в существующем `.env` выставьте:

```dotenv
QWEN_CONTEXT_TOKENS=0
QWEN_BATCH_TOKENS=120000
QWEN_PARALLELISM=1
```

Затем:

```bash
sudo systemctl restart matchlab.service
cd /root/matchlab
.venv/bin/python -m matchlab check-qwen-load
```

Размер входной части задаётся отдельно от окна движка. С этими настройками
измеренный вход в 100784 токена может отправляться крупной частью; отдельное
ограничение числа записей также может разделить его. Итоговый синтез остаётся
отдельным вызовом. Будущие более крупные контексты разбиваются без удаления данных.
Проверьте покрытие и время одного настоящего разбора, наблюдая за обоими проектами:

```bash
sudo journalctl -u matchlab.service --since '10 minutes ago' --no-pager \
  | grep -E 'Qwen (event|part|completion)'
```

Таймауты не увеличиваются автоматически. Большое окно не подтверждает скорость
и качество аналитики; это проверяется реальными запросами.

## Другие способы запуска

Если unit или путь отличается, сначала выполните `inspect --unit vllm.service`.
Эта команда показывает способ запуска, имена переменных и числовой параметр
окна, скрывая значения ключей. Она не создаёт план и ничего не меняет.

`prepare` без `--launch-script` по-прежнему поддерживает один явный числовой
параметр в ExecStart и готовит отдельный drop-in. Это другой тип плана;
`apply` и `rollback` выбирают действие по его формату. Обёртки, переменные,
неоднозначные аргументы и существующие drop-in не переписываются автоматически.

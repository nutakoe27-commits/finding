# Общее окно Qwen: подготовка перехода на 128K

В измеренном разборе исходные данные занимают 73799 токенов, а запрос с ID
источников и метаданными — 100784. С резервом требуется 103088. Для отправки
такого запроса целиком подходит окно 131072, а 65536 недостаточно.
Это размер текущего формата, а не обязательный размер для любых будущих матчей.
Matchlab также умеет передавать все данные частями в прежнее окно 32768.

Фактический артефакт: `mattbucci/Qwen3.8-27B-AWQ`; прежний API-алиас:
`QuantTrio/Qwen3.5-35B-A3B-AWQ`. В опубликованном config.json указано
262144 позиций. Это подтверждает предел модели, но не доступный KV-кэш
запущенного экземпляра на двух V100 32 ГБ.

## Влияние на второй проект

Используется одна общая `vllm.service`. Перезапуск прервёт текущие запросы
обоих проектов до завершения загрузки модели. Сохранение алиаса, порта,
ключей, AWQ, float16, TP=2, доли GPU 0.82 и `max-num-seqs=4` сохраняет
настройки доступа. Длинный запрос всё равно делит GPU и KV-кэш со вторым
проектом, поэтому прежняя задержка ответов не гарантируется.
Второй процесс той же модели без отдельного бюджета памяти не запускается.

Увеличивать окно необязательно: вариант без перезапуска модели — подобрать
`QWEN_BATCH_TOKENS` и время по `check-qwen-load` на VPS, оставив окно 32768.
Это затрагивает клиент Matchlab и требует нескольких последовательных вызовов.

## Подготовка на сервере нейросети

Из чистого checkout репозитория:

```bash
(
  set -e
  cd ~/matchlab-scraper-src
  git pull --ff-only origin main
  sudo python3 scripts/configure_qwen_context.py prepare \
    --unit vllm.service --tokens 131072
)
```

`prepare` только читает загруженную службу и создаёт закрытый план с резервной
копией в `/var/lib/matchlab-qwen-context`. Проверяет кандидат через
`systemd-analyze verify`. Исходный unit не меняется, drop-in не устанавливается,
daemon-reload и перезапуск не выполняются. В выводе нет содержимого unit-файла,
ключей или переменных окружения. Приватные файлы плана не нужно присылать в чат.

Поддерживается один явный ExecStart с числовым `--max-model-len`, включая
продолжения строк. Если запускается shell-обёртка, значение берётся из переменной
или уже существуют drop-in, инструмент остановится для отдельной проверки.
Автоматически не переписывает неизвестный способ запуска.

Результат содержит изменение только `--max-model-len`, путь плана и готовые
`apply_command` / `rollback_command`. `kv_capacity_verified=false` означает,
что вместимость GPU ещё не подтверждена: `systemd-analyze` проверяет unit,
а не выделяет KV-кэш модели.

## Применение в выбранное окно обслуживания

Сначала сохраните `rollback_command` из результата prepare. Затем выполните
ровно выведенный `apply_command`: он установит
`/etc/systemd/system/vllm.service.d/90-matchlab-context.conf` и выполнит
daemon-reload. Аргументы исходного ExecStart сохраняются, кроме числа окна.
Сам процесс продолжит работать с прежним окном до явного перезапуска.

Если исходный unit или набор drop-in изменился после подготовки, применение
остановится. Существующий файл с тем же именем не перезаписывается.

Когда текущие запросы обоих проектов можно прервать:

```bash
sudo systemctl restart vllm.service
sudo systemctl show vllm.service -p ActiveState -p SubState -p NRestarts --no-pager
```

`active` во время загрузки само по себе не означает готовый API.
На VPS дождитесь восстановления `check-qwen` и проверьте `inspect-qwen-context`:

```bash
cd /root/matchlab
.venv/bin/python -m matchlab check-qwen
.venv/bin/python -m matchlab inspect-qwen-context
```

Нужно увидеть настоящий ответ Chat Completions и `context_tokens=131072`.
Проверьте также один обычный запрос второго проекта. Если модель не загружается,
повторно падает, API остаётся недоступным или второй проект перестал работать,
выполните сохранённый `rollback_command`, затем:

```bash
sudo systemctl restart vllm.service
```

Откат удаляет только неизменённый drop-in этого инструмента и вызывает
daemon-reload. Исходный unit, чужие drop-in и ручные изменения не удаляются;
изменённый вручную файл инструмента требует отдельной проверки.
Не используйте `systemctl revert`: он может удалить настройки другого проекта.

## Настройки Matchlab после успешной проверки модели

Только на VPS в существующем `.env` выставьте:

```dotenv
QWEN_CONTEXT_TOKENS=0
QWEN_BATCH_TOKENS=120000
QWEN_PARALLELISM=1
```

Перезапустите только `matchlab.service`. Это позволяет запросу с 100784 токенами
поместиться в одну входную часть, если не сработают дополнительные ограничения
на число записей; итоговый синтез остаётся отдельным вызовом.
Будущие более крупные контексты продолжат разбиваться, данные не отбрасываются.
Лимиты времени не увеличиваются автоматически: сначала выполните
`check-qwen-load`, затем один реальный разбор при наблюдении за обоими проектами.
Большое окно само по себе не подтверждает ни скорость, ни качество аналитики.

```bash
sudo systemctl restart matchlab.service
cd /root/matchlab
.venv/bin/python -m matchlab check-qwen-load
sudo journalctl -u matchlab.service --since '10 minutes ago' --no-pager \
  | grep -E 'Qwen (event|part|completion)'
```

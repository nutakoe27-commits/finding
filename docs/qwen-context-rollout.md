# Qwen 128K: один контролируемый тест и откат

На сервере работают 1Cat-vLLM на двух V100 32 ГБ, Kokoro и Whisper на GPU 0.
Успешно проверенный профиль Qwen: окно 32768, gpu-memory-utilization=0.82,
max-num-seqs=4 и max-num-batched-tokens=8192.

## Что установлено диагностикой

- 128K / 0.82: CUDA OOM при инициализации. Дополнительное выделение 848 МиБ
  не поместилось при примерно 833 МиБ свободной памяти GPU 0.
- 128K / 0.70: сервер дошёл до первого запроса из 19 входных токенов, затем
  упал в `recompute_w_u_fwd -> Triton autotuner -> do_bench` операции Gated DeltaNet.
- `/models` и `/tokenize` продолжали отвечать после `EngineDeadError`.
  Сообщение окна 131072 не подтверждает исправность генерации.
- API вернул HTTP 200 при ошибке ядра. Клиент распознаёт объект ошибки
  и не считает его результатом Chat Completions; диагностика нагрузки
  останавливается перед следующим запросом при неправильной структуре ответа.

Установленный tokenizer отдельно задан как `QuantTrio/Qwen3.6-27B-AWQ`,
модель — `mattbucci/Qwen3.8-27B-AWQ`, API-алиас —
`QuantTrio/Qwen3.5-35B-A3B-AWQ`. Совместимость токенизатора требует отдельной
проверки; этот параметр не меняется одновременно с исправлением OOM.

## Проверочный профиль

Это экспериментальный профиль, а не подтверждённая рабочая конфигурация.
Изменение требует перезапуска общей vllm.service. Текущие запросы Qwen обоих
проектов прервутся до загрузки модели. Whisper и Kokoro остаются работать.

Для автоматической замены параметров на сервере нейросети:

```bash
cd ~/matchlab-scraper-src &&
git pull --ff-only origin main &&
sudo python3 scripts/set_qwen_profile.py --profile 128k
```

Команда сохраняет закрытую копию, проверяет shell-синтаксис и атомарно обновляет
файл с сохранением владельца и прав. Она не управляет службами.
Известный рабочий набор параметров возвращается той же командой с
`--profile 32k`. Это восстановление профиля, а не копирование потенциально
уже неработавшего файла из последнего эксперимента.

Для ручного изменения вместо этого скрипта сохраните копию и откройте запуск:

```bash
cd /home/user/1Cat-vLLM &&
qwen_trial_dir="$(sudo mktemp -d /var/tmp/vllm-final128k.XXXXXX)" &&
sudo cp -a start_vllm38.sh "$qwen_trial_dir/original.sh" &&
printf 'Копия текущего файла: %s\n' "$qwen_trial_dir/original.sh" &&
sudo nano start_vllm38.sh
```

В существующей команде поменяйте значения, не дублируя флаги:

```text
--max-model-len 131072 \
--gpu-memory-utilization 0.60 \
--max-num-batched-tokens 2048 \
--max-num-seqs 2 \
--enable-chunked-prefill \
--enforce-eager \
```

Сохраните остальные аргументы и правильные продолжения строк. Если последний
аргумент завершает команду, у него не должно быть лишнего `\`.
`--enforce-eager` отключает CUDA Graphs / torch.compile, но не Triton-ядра
и их autotuning. Меньший бюджет, prefill и число слотов дают больше запаса
для временных буферов. Скорость и параллельная ёмкость могут уменьшиться.
Точный допустимый размер контекста подтверждается настоящим запросом.

Не добавляйте одновременно ручной `--kv-cache-memory-bytes`: он переопределяет
автоматическое определение размера кэша через gpu-memory-utilization.
В этом тесте не устанавливайте новые пакеты и не редактируйте Triton / 1Cat.

```bash
sudo bash -n /home/user/1Cat-vLLM/start_vllm38.sh &&
sudo systemctl reset-failed vllm.service &&
sudo systemctl restart vllm.service
```

Смотрите только новые сообщения (Ctrl+C завершает просмотр, а не службу):

```bash
sudo tail -n 0 -F /var/log/vllm.log
```

После `Application startup complete` выполните на VPS один короткий тест:

```bash
cd /root/matchlab
.venv/bin/python -m matchlab check-qwen
```

Успех — `chat_completions: ok`. При OOM, EngineDeadError, повторных падениях
или отсутствии рабочего короткого ответа не запускайте большой контекст.
Верните рабочий профиль ниже, сохранив лог для дальнейшего изучения.

## Рабочий откат 32K

Сохранённая выше копия отражает файл перед последним тестом и могла содержать
уже неработающий профиль 128K / 0.70. Она не считается проверенным откатом.

В `start_vllm38.sh` верните:

```text
--max-model-len 32768 \
--gpu-memory-utilization 0.82 \
--max-num-batched-tokens 8192 \
--max-num-seqs 4 \
```

Удалите добавленный в эксперименте `--enforce-eager`. Chunked prefill
можно оставить явно включённым: в рабочем профиле он уже был включён.
Проверьте синтаксис и перезапустите только vllm.service теми же командами.
Затем подтвердите короткий Chat Completions на VPS.

## Matchlab после успешного теста модели

Текущая версия сначала отбирает основные рынки (`QWEN_MARKET_LIMIT=8`), сохраняя
полный вход отдельно для аудита. Для выбора окна сравните один и тот же снимок
до и после отбора без генерации:

```bash
cd /root/matchlab
.venv/bin/python -m matchlab compare-qwen-context
```

`focused.input_tokens` — вход после отбора, а `focused.minimum_context_tokens`
учитывает резерв ответа. Сравнение с полным входом находится в `full` и `savings`.
Статистика и история не сокращаются, поэтому уменьшение числа рынков не
гарантирует перехода на 32K. Настройки общей vLLM этим обновлением не меняются.

После короткого ответа проверьте `inspect-qwen-context`. Окно 131072 вмещает
сохранённый запрос из 100784 входных токенов с резервом, но не доказывает,
что его инференс укладывается в ресурсы и время.

В тестах первый фрагмент получил 112455 входных токенов и был оборван
клиентом через 90 секунд. После перехода на один вызов полный вход из 115116
токенов также не завершился за 140 секунд. В показанных логах текущий процесс продолжал
обслуживать запросы; новая ошибка OOM не обнаружена. Это подтверждает таймаут
клиента, но не завершение большого разбора. Интервальные показатели throughput
объединяют нагрузку обоих проектов и не дают точного времени такого запроса.

Matchlab проверяет возможность отправить все записи сразу и в этом случае
получает конечные аргументы за один вызов, без второго этапа генерации.
Точные цитаты проверяются сервером; все исходные поля сохраняются.
Если полный вход не помещается, остаётся обработка по частям.

Для одного контролируемого теста настройте `.env` **на VPS сайта**:

```dotenv
QWEN_CONTEXT_TOKENS=0
QWEN_BATCH_TOKENS=128000
QWEN_PARALLELISM=1
QWEN_ENABLE_THINKING=false
QWEN_TIMEOUT_SECONDS=140
QWEN_ANALYSIS_TIMEOUT_SECONDS=150
QWEN_JOB_TIMEOUT_SECONDS=900
```

После обновления кода и изменения `.env` нужен перезапуск только matchlab.service.
Модель и голосовые службы для этой правки не перезапускаются.
Выполните `inspect-qwen-context`: `fits_advertised_window` проверяет окно с
резервом, а `input_tokens` также должен укладываться в `batch_token_limit`.
Затем проверяйте один настоящий разбор с наблюдением за очередью обоих проектов.
При полном помещающемся входе ожидаются `model_calls=1`, `parts_completed=1`
и `parts_total=1`, а число обработанных рынков должно совпасть с общим.
Ошибочные разборы кэшируются максимум 30 секунд; старые записи не переписываются.
Кнопка сайта использует фоновое задание с отдельным пределом в 900 секунд.
Браузер получает HTTP 202 и опрашивает его состояние, результат сохраняется
в истории. После перезагрузки страницы повторное нажатие на том же матче
продолжает активное задание. Синхронный предел 140 секунд действует на старый
`/explain` и короткие диагностические запросы, а не на фоновую генерацию.
Входные поля сохраняются; объединение более крупных записей уменьшает
дублирование путей и метаданных. Скорость генерации на V100 этим не гарантируется.
При повторном таймауте не отправляйте несколько разборов подряд: предыдущая
генерация может ещё занимать модель. Даже предел в 15 минут требует проверки
на реальном контексте при нагрузке обоих проектов.
Не утверждайте готовность 128K до успешного выполнения реального запроса.

Обновление на VPS сайта (нейросеть и голосовые службы не перезапускаются):

```bash
cd /root/matchlab &&
git pull --ff-only origin main &&
.venv/bin/python -m matchlab.manage backup &&
sudo systemctl restart matchlab.service
```

После обновления страницы запустите один разбор. Смотреть новые сообщения:

```bash
sudo journalctl -u matchlab.service --since '5 minutes ago' -f -o cat \
  | grep --line-buffered -E 'Analysis job|Analysis queue|Qwen'
```

Завершение задания подтверждается `Analysis job finished`. Успех именно
генерации — `Qwen event complete: state=ready`; `completed` у задания также
может означать завершение расчётной сводкой, если модель не ответила.

Генерация на входе 69865 токенов завершилась за 119.7 секунды с 194 токенами
ответа и `finish=stop`. Затем цитата была отклонена как `quotation_mismatch`.
Прежний обработчик ошибочно относил сообщение «Нет обработанных частей контекста»
к переполнению окна. Исправлены классификация и пояснение в админке.
Это отдельная ошибка проверки ответа, не свидетельство недостаточного окна.
В текущем протоколе модель ссылается на ID подтверждённых фактов и пишет
подробные объяснения их значения. Сервер вставляет исходные факты и числа;
выдуманные ссылки и неподтверждённые числа отклоняются. Допускается одна короткая попытка исправления,
без повторной отправки большого входа. Если банка фактов нет, резервный протокол
по-прежнему проверяет цитаты и числа. Интернет-поиск в новых разборах отключён по запросу владельца сервиса;
автоматический сбор Winline, архив и все рынки остаются в работе.

Сравнение сохранённого снимка от 10.11.2026 в прежнем протоколе показало:
полный вход — 51 рынок / 154 исхода, 53782 входных токена; после отбора —
0 рынков, 35854 токена (минимальное окно с резервом — 36622).
Сама статистика занимала 74024 байта. Оба запроса помещались в объявленные
131072 токена; возврат к 32768 не вместит этот снимок даже без рынков.
Пустой отбор не доказывает отсутствия рынков у сборщика. Для потоковой
предматчевой линии предел свежести исправлен с 45 до 180 секунд; live остаётся
45 секунд. Если свежих доступных рынков нет, сохранённый основной рынок
остаётся только для контекста, без расчёта процентов по его ценам.
Эти изменения устанавливаются на VPS; параметры vLLM и службы озвучки не меняются.

Для чтения структуры systemd-запуска без ключей доступен
`scripts/configure_qwen_context.py inspect --unit vllm.service`.
Старый `prepare --tokens 131072` меняет лишь число окна и не делает данный
проверочный профиль: повторять с ним уже падавший запуск не следует.


Текущая версия использует наблюдённые популярные карточки Winline и сезонные
средние без порога в 30 матчей. Подробности и установка сборщика:
[независимая модель и популярные рынки](independent-model.md).
